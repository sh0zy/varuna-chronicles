# ヴァルナ 制作工程・品質判定・進捗管理

版：2026-09-21。設計内容は `game-design.md`、原要求は `source-request.txt`、初期実装計画は `superpowers/plans/2026-09-21-varuna-first-playable.md` を参照。

## 1. 現在地と成果物の区別

今回の初期制作は、ローカルで動く三人称のブラウザ検証版と、完成版へ向けた制作仕様をつくる工程である。**245〜330時間の完成ゲーム、完成品質の30〜60分の垂直スライス、初期検証版を同一視しない。** 初期検証版は操作・地形・見せ方・進行の検証に使い、実プレイ時間と映像品質は実機確認後に記録する。

この文書の「設計済み」は、制作を始められる案があるという意味で、モデル、台詞、アニメーション、AI、音、テストが揃ったという意味ではない。

| --- | --- | --- | --- | --- |
| 世界・人物・五幕・四勢力 | 初稿作成 | 手帳の一部へ接続予定 | 未制作 | 台詞、分岐表、実プレイでの理解確認 |

## 2. 技術選定と試作の用途

初期実装計画では、TypeScript、Three.js、ViteによるローカルWebGLゲームを採用する。地形とモデルを手続き生成し、外部サービスや素材ダウンロードをプレイ中に必須としない。UIはDOMで日本語の手帳、地図、設定を構成し、進行と保存を描画から分けて検証する。

この選択は、短い導線で操作と画面を確認しやすいという初期検証の都合による。映画的な動的照明、高密度の広域世界、大量の専用アニメーション、筋肉・皮膚表現を完成版で実現できることの証明にはしない。

| 候補 | 本作で評価する点 | 先に確認する制約 | 判断 |
| --- | --- | --- | --- |
| Unreal Engine系のネイティブ制作 | 広域世界、動的照明、密度の高い資産、映像制作との統合 | 実際のインストール、プロジェクト作成・ビルド、対象GPU、ライセンスと素材条件 | 高品質本制作の有力候補。版と機能の採用は環境確認後に確定 |
| Unity系のネイティブ制作 | 独自の生態シミュレーション、制作ツール、描画の調整 | 採用レンダーパイプライン、広域地形・植生・アニメーションの総合試験 | 比較対象。機能名だけで優劣を断定しない |
| Three.js/WebGLの初期検証 | 操作・レイアウト・地形・進行をすぐ起動して確認 | ブラウザのメモリ、描画・入力の制約、資産制作基盤 | 今回の検証版に採用。完成版の性能保証とは別 |

完成版を別エンジンに移す場合、持ち越すものはID付きの内容データ、脚本、地形の意図、テストケース、操作検証の知見。レンダラー、入力、物理、保存のI/Oは移植先に合わせて再実装する。画面を包むだけでネイティブの完成品質へ到達したとは扱わない。

## 3. グラフィック優先の資産工程

量産の前に、草原の代表眺望、樹海の水辺、オルガの接写・歩行・突進の4場面を品質見本にする。量産後に全種の輪郭を直す事態を防ぐため、最初の一体で骨格から画面まで工程を通す。

| 工程 | 入力 → 成果物 | 品質判定・次工程への条件 |
| --- | --- | --- |
| 視覚調査・コンセプト | 世界設定 → シルエット、色、寸法基準、接写と遠景のラフ | 大きさと生態が輪郭だけでも伝わる。創作と学術的着想を区別 |
| 造形 | 承認した姿と生態 → 高解像度モデル、ゲーム用モデル、UV | 関節が必要な可動域を持つ。足・角・嘴など接触部の寸法を統一 |
| 素材 | 部位と環境 → 色、粗さ、法線、濡れ、傷、毛・羽の資産 | 過剰な光沢を避け、逆光・日陰・雨・夜で崩れない |
| 骨格と変形 | 造形 → リグ、接地、視線、呼吸、筋肉・皮膚の遅れ | 重心が支持脚を外れない。首・尾・腹が貫通しない |
| アニメーション | 行動仕様 → 歩行、走行、食事、警戒、威嚇、負傷、段階遷移 | 突然の方向転換や滑りがない。予告と実際の当たりが一致 |
| 生態AI | 状態図と行動資産 → 日課、群れ、感覚、環境作用 | 観察中に理由が分かる。逃げ場・幼体・天候への反応がある |
| 環境 | 地形と水系 → 地層、岩、植生、水、廃墟、天候 | 道とランドマークが読める。地形の根拠と地域境界が自然 |
| 照明・音 | 地域の色と生態 → 時刻・天候、反射、霧、空間音 | 重要情報を光と音の片方だけに依存させない |
| 最適化 | 最悪条件の実測 → 詳細段階、インスタンス、距離別更新 | 画面内の重要物を守りつつ予算内へ。静止画だけで評価しない |
| 出荷資産化 | 検証済み資産 → 出典、利用条件、命名、依存一覧 | ライセンスが確認できる。仮素材・生成物・最終資産を区別 |

足元の草、水しぶき、泥、接地音、カメラの揺れを一つの体重情報から整合させる。近景の皮膚を精細化する前に、歩行速度と脚運びの不一致を直す。画面の美しさを損なうUIや輪郭のちらつきも、グラフィック課題として扱う。

## 4. 完成品質の垂直スライス

依頼された垂直スライスの目標は30〜60分。初期検証版を実測せず、この時間に達したと説明しない。以下の内容が完成品質で連続して遊べ、外部の初見者が到達できることを完成条件にする。

| 区間 | 体験と必要機能 | 合格条件 |
| --- | --- | --- |
| 0〜導入 | 草海の朝、主人公操作、群れの通過 | 開始直後から通常操作。地形・カメラ・移動が安定し最初の眺望へ届く |
| 初観察 | 草食・捕食・小型生物、痕跡と風向 | 各生物が異なる行動。手帳へ重複なしで記録し、観察に意味がある |
| 寄り道 | 短い依頼、騎乗、小遺跡 | 引き返し可能。目的の変化、報酬、図鑑、拠点への帰還がつながる |
| オルガ調査 | 幼体の足跡、共振装置、現地準備 | 戦闘の解を事前に推理できる。準備の有無が対処に影響 |
| オルガ対峙 | 予告、突進、地形利用、弱点、決着 | 押し続けるだけで終わらず、初心者が攻撃理由を説明できる |
| 地域の変化 | 根道開通、群れと住民の変化 | 再読込後も変化を保持。新しい景観と通行に触れられる |
| 再開と設定 | セーブ、音量、入力、文字、写真 | 中断後の進行を復元。見える設定は実際に効果がある |

初見者が迷った位置、痕跡の見落とし、戦闘の失敗原因を観察する。到達時間が短い場合に、遠回りの強制や敵HP増加で埋めない。固有の発見や意思決定が足りているかを見直す。

## 7. 245〜330時間を検証する方法

| 主目的カテゴリ | 本編外の追加時間 | 本編を含む時間枠 |
| --- | --- | --- |
| 本編 | — | 75〜90時間 |
| 地域サイド物語 | 45〜60時間 | 本編と別の目的を実際に進めた時間 |
| 生態研究・図鑑 | 30〜40時間 | 独立した観察・調査の時間 |
| 遺跡・洞窟・秘境 | 30〜45時間 | 本編必須区間を除く探索の時間 |
| 育成・装備・攻略課題 | 25〜35時間 | 必要な試行と新しい組み合わせの時間 |
| クリア後の物語と遠征 | 40〜60時間 | 他のカテゴリへ同じ時間を重複算入しない |
| **合計** | **170〜240時間** | **245〜330時間** |

1日3時間なら245時間は約82日、330時間は110日。これは毎日プレイを要求する意味ではなく、時間目標の換算である。主要サイドと探索を一部まで遊ぶ層は150〜200時間を別の到達目安にする。

### 重複しない計測

1. セッションには連続した時間軸を一つだけ持たせる。各時間区間を一つの主目的カテゴリへ割り当てる。
2. 本編移動中に図鑑が進んでも、その時間は本編にだけ計上する。研究の完了状況は更新するが、追加の研究時間を発生させない。
3. 遠征中に素材を得ても、その時間は遠征にだけ計上する。育成時間は別途構成を試した時間だけ。
4. メニュー放置、アプリ非アクティブ、読み込み、検証用操作、開発者のデバッグ、強制待機を除外して記録する。
5. 再挑戦時間は通常プレイの総時間に含めるが、死亡・移動・新規発見・戦闘・会話をタグ付けして水増しを検出する。熟練者の名誉課題は全達成時間から除外。
6. 一周だけの開発者走行で結論を出さない。初見、探索好き、戦闘熟練など複数の層で、中央値とばらつき、完了率、疲労を確認する。

記録項目例：`buildId, playerCohort, sessionId, intervalStart, intervalEnd, primaryCategory, objectiveId, activityTag, completedIds, deaths, hintsUsed`。個人識別情報を収集する必要はない。テレメトリだけに頼らず、初見観察と手動の時間記録でも同じ分類を使えるようにする。

目標未達なら、「時間が短いが発見が豊富」なのか「同じ活動が重複している」なのかを分ける。面白さが成立した短い内容へ不要な待ち時間を足さない。固有の発見・判断を追加できる制作余力がなければ、未達と明記して規模計画を改訂する。

## 8. 技術予算と性能の測り方

以下は完成版の**仮の目標であり、実測結果・推奨PC仕様ではない**。対象CPU・GPU・メモリ・OS・解像度・品質設定は、品質見本の測定後に確定する。

| 指標 | 仮の品質目標 | 記録方法 |
| --- | --- | --- |
| 操作応答 | 60fpsを基準とする操作設計。画質優先設定との両立を評価 | 16.7msを基準にCPU/GPU時間、P50/P95/P99、入力から描画までを記録 |
| 描画の安定 | 通常探索・群れ・水辺・ボス戦で突発的な長い停止を減らす | 平均fpsだけでなくフレーム時間のグラフと最悪場面 |
| メモリ | 対象機で安全な上限と余裕を確保 | 起動、地域境界、セーブ読込、長時間後のRAM/VRAM、増加傾向 |
| 読み込み | 境界で操作が長時間止まらない | 初回／再訪、低速ストレージ、連続移動の待ち時間 |
| 保存 | 失敗時に正常な以前の保存を残す | 中断・破損・容量不足・旧バージョンの再現試験 |
| 生態計算 | 近景の観察を優先し、遠方は整合する概略へ | 個体数・更新頻度・CPU時間・再出現の連続性 |

ブラウザ検証版は、ブラウザ名と版、GPU描画経路、画面サイズ、画質設定、実際の計測方法を添える。ヘッドレスやソフトウェア描画の数字をユーザーのGPU性能に換算しない。表示したfpsだけで製品性能の保証をしない。

各品質見本は同じカメラ経路を再生し、晴れ・雨・夜、徒歩・騎乗、少数個体・群れ・戦闘を比較する。詳細段階の境界を跨いだ移動映像を保存し、静止画で隠れるポップやちらつきも審査する。

## 9. 検証の優先順位と受け入れ基準

初期検証版では、保存の正規化、進行条件、報酬の一回性、ボスの攻撃可能条件など、壊れるとプレイを損なう純粋な状態処理を自動テストする。見た目と操作は実際の起動で検証する。実装と同じ処理をなぞるだけのテストで数量を増やさない。

| 分野 | 必要な検証 | 合格の証拠 |
| --- | --- | --- |
| 構築 | 型検査、製品ビルド、起動 | 実行コマンド、終了コード、ビルド識別子 |
| 進行 | 初回発見、同じ発見の再実行、順不同の調査 | 重複報酬なし、手帳と地図の状態一致 |
| 戦闘 | 保護中／弱点露出中／決着後の攻撃 | 状態に合うダメージ、予告、復帰、勝利は一度だけ |
| 保存 | 新規、継続、再読込、破損、未来版 | 状態が壊れずエラーから戻れる。勝利と経路開通を保持 |
| 移動 | 斜面、水際、段差、騎乗、落下、ボス付近 | 地形抜け、カメラ埋没、永続的な操作不能がない |
| UI | 手帳、地図、設定、停止、写真、再開 | すべての可視操作に実際の結果。閉じた後の入力が正しい |
| 入力 | キーボード・マウス、ゲームパッド、途中切替 | 操作説明と入力が一致。メニューとゲームの入力が競合しない |
| 音 | 初回ジェスチャー、音量ゼロ、復帰 | 自動再生制約で開始不能にならず、ミュートが実際に効く |
| グラフィック | 実画面と移動動画、代表眺望、ボス接写 | 輪郭、光、水、動きが意図どおり。仮素材であることを明記 |
| 完成版脚本 | 四体の24順序、討伐／解放、結末条件 | 未知情報の先取り、人物の不在会話、分岐の永久欠損がない |

受け入れ記録は「実施日／環境／ビルド／手順／期待／実結果／証拠／残課題」を持つ。「動いたはず」では完了にしない。検証で不具合が出た場合は、原因と再現条件を特定してから修正し、影響する範囲を再確認する。

## 10. リスクと対処

| リスク | 早期に見つける方法 | 対処 |
| --- | --- | --- |
| 90種で資産品質が薄まる | 一体の造形〜AI〜音の実制作量を測る | 骨格の共有と専用行動を分ける。種数を完成偽装しない |
| 世界が広いだけになる | 寄り道率、迷い、静かな時間と退屈な時間を観察 | 地図面積より眺望・発見・判断の密度を調整 |
| 生態が予想外に破綻する | 群れの長時間観察、遠近の切替、保護種の再訪 | 概略状態と実個体を対応。重要種を永久絶滅させない |
| 大型敵のカメラが読めない | 壁際、足元、騎乗中、画面端で攻撃を受ける試験 | 予告とカメラ距離・遮蔽を一緒に調整 |
| 自由順で脚本が崩れる | 24順序の状態遷移と台詞前提の検証 | 局所の事実と解釈を分離。既知情報を集合で管理 |
| 結末後に内容が欠ける | 各結末から全達成の再現 | 代替文脈、章再訪、共有報酬を設計段階で用意 |
| 画質に対して性能が不足 | 品質見本でGPU/CPU時間を分離計測 | 重要物優先の詳細段階、影・植生・更新頻度の調整 |
| 保存仕様の変化で進行が消える | 旧版データと中断・破損試験 | バージョンと移行、バックアップ、検証後の書込 |
| 時間目標を作業で埋める | カテゴリ別の重複排除、失敗時間の内訳 | 固有の遊びを追加。達成していない目標は未達と報告 |

## 11. 次の担当者へ

まず現在の実行可能なビルドを起動し、READMEの実装一覧と実画面を照合する。設計書の予定機能を見て実装済みと推測しない。新しい内容は既存のIDへ対応付け、画面上の価値、必要な判断、成長による違いを定めてから制作する。

最優先の次段階は、初期検証版の観察結果を基に、オルガと草海の一部を完成品質へ近づけること。全地域を急いで薄く増やすよりも、一つの連続した体験で本作の映像・探索・戦闘・保存の基準を確かめ、その工程を全編へ展開する。
