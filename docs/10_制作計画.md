## 2. エンジンの比較

この作品に必要なもの：広域の描画とストリーミング、巨大生物のアニメーション（重さ・二次運動・足の接地）、多数の生物のシミュレーション、植生と地形、水と潜水、保存の安定性。

| 候補 | 描画 | 広域ストリーミング | 生物のアニメーション | 植生・地形 | 保存・道具 | この作品での評価 |
|---|---|---|---|---|---|---|
| **Unreal Engine 5** | Nanite・Lumen・仮想シャドウで大規模な自然景観に強い | World Partition・データ層・HLOD | Control Rig、IK Rig、モーションマッチング、Chaos による二次運動 | 手続き的な植生配置（PCG）、ランドスケープ | 標準の保存の仕組み、大規模チーム向けの道具 | **製品版の第一候補**。描画品質を最優先にする方針と最も合う |
| Unity 6（HDRP） | HDRP は高品質だが、大規模な自然には調整が必要 | アドレッサブル＋独自の区画読み込み | Animation Rigging、DOTS で多数の個体 | Terrain＋独自の植生 | 柔軟 | 次点。DOTS による大量の生物は強いが、描画品質を出すための開発量が多い |
| Godot 4 | 近年向上したが、大規模な自然景観の描画は発展途上 | 独自実装が必要 | 基本的な機能 | 独自実装 | 軽量 | 規模に対して不足 |
| Web（Three.js／WebGL2） | 描画の上限が低い（本格的な GI・仮想シャドウなし） | 独自実装 | 手続き的なスケルトン | 独自実装 | ブラウザの保存領域 | **今回の垂直スライスで採用**：この開発機で実際に動かして測れる唯一の環境だったため。製品版には不向き |

### 2.1 採用の判断

- **製品版：Unreal Engine 5（推奨）**。前提条件：
  1. 開発機に単体GPU（RTX 3070 級以上、VRAM 8GB 以上）を用意する。この開発機（Iris Xe）では、Lumen・Nanite を使った品質の判断ができない。
  2. 巨大生物のアニメーションを担当できる技術者（テクニカルアニメーター）を確保する。
  3. 対象機器の最低構成を、プロトタイプで実測してから決める（**実測なしに「高画質で安定動作する」とは言わない**）。
- **垂直スライス（今回）：Three.js＋TypeScript**。目的は、見た目の完成品質ではなく、**遊びの設計（生態を読む・痕跡・誘導する戦闘・結末につながる選択）が面白さとして成立するか**を、実際に操作して確かめること。この区間で確かめた仕様と数値は、エンジンに依存しない形で `src/` と `docs/` に残してあり、UE5 へ移すときの基準になる。

## 5. 工程と依存関係

```
[0] 垂直スライス（試作）──→ [1] 製品版の垂直スライス（UE5、完成品質の見本）
                                   │
          ┌────────────────────────┼─────────────────────────┐
          ▼                        ▼                         ▼
 [2a] 生物の骨格系統と     [2b] 地形・植生・天候の     [2c] 物語・会話・
      アニメーション基盤         制作の流れ（PCG）           クエストの道具
          │                        │                         │
          └──────────┬─────────────┴──────────┬──────────────┘
                     ▼                        ▼
            [3] 第2幕の4地域（中ボス4体）  [3'] 峡谷・火口帯（任意地域）
                     │
                     ▼
            [4] 星骸の盆地・原環の心臓・アーケア（第3〜5幕）
                     │
                     ▼
            [5] クリア後（遠征12本・古代の記憶・最終仮説）
                     │
                     ▼
            [6] 通しのプレイテストと時間の検証（09）→ 調整 → 完成
```

**主な依存関係**：
- 生物の骨格系統（2a）ができるまで、地域の生態系（3）は仮の生物で作る。
- 4体の中ボスは攻略順が自由なので、「総合の理解」の出し分け（`02`）の仕組みを、最初の中ボスより前に作る。
- アーケアの最終戦（4）は、救った集落・回遊路・協力した生物が戦闘に返ってくるので、第2幕のすべての決着の状態が定まってから調整する。
- プレイ時間の検証（6）は、各段階で部分的に行う（`09` の検証の段階）。

## 6. 体制・期間・費用の見積もり（前提つき）

**以下は、同規模の商業作品の一般的な規模から置いた前提による概算であり、約束ではない。** 実際の値は、製品版の垂直スライス（工程1）を作ったときの実績から見積もり直す。

| 前提 | 値 |
|---|---|
| チームの規模（最盛期） | 80〜150人（外部の協力会社を含む） |
| 工程1（製品版の垂直スライス） | 20〜30人で 12〜18か月 |
| 全体の期間 | 工程1の後、4〜5年 |
| 費用 | 人件費を中心に、数十億円規模（地域・雇用形態で大きく変わる） |

**短期間での完成は約束しない。** 特に、生物のアニメーションと、自由な攻略順を支える物語の分岐の検証は、見積もりが外れやすい。

## 7. この垂直スライスのコードの構成

| フォルダ | 内容 |
|---|---|
| `src/core/` | 入力（キー・マウス・パッドの統一と割り当て変更）、設定、時計と天候、ノイズ、音 |
| `src/world/` | 配置（layout）、地形、大気と霧のシェーダー、空、草、植生、水、遺跡と野営地、痕跡と効果、静的な物の結合 |
| `src/creatures/` | 骨格ビルダー、手続き的な歩行、種の定義（図鑑の文章を含む）、個体、生態系、翠角王オルガ |
| `src/player/` | 人の姿、プレイヤーの操作、カメラ |
| `src/game/` | 状態とセーブ、物語データ、野営地の人々、ゲーム全体の統合 |
| `src/ui/` | すべての画面（DOM） |
| `tools/` | 自動の検証（撮影・計測・通しプレイ・入力・ボス戦・依頼） |
| `tests/` | 単体テスト（セーブの検証など） |
